# sql test perspectives

These *test perspectives* say what a TC under `sql/` checks. How to write the files of the TC is in the [*writing rules*](writing-rules.md).

## Scenarios to cover

**Give each scenario of the Jira issue a case, whether the issue describes it in its description, its acceptance criteria, a comment, or an attached file.** A regression in a scenario that no case runs goes unseen. Example: the issue describes two queries and attaches a script with a third, so the TC has Case 1 to Case 3, one for each.

**Next to the case that reproduces the issue, add cases with boundary values and invalid inputs, and run the same operation through the related functions and DML statements.** A regression often shows only at an edge of the input range or in a sibling of the reported function. For a function or an operator, the edges include the minimum and the maximum of the type, `NULL`, the empty string, an empty table, and another collation, and a bound gets a case just below it, on it, and just above it. Example: a TC for an `ADDDATE` fix also runs the INT amount `-2147483648` and a `NULL` amount, and runs the same amounts through `SUBDATE`, `DATE_ADD`, and `DATE_SUB`.

**When a result can depend on the state of a transaction, check it inside an `autocommit off;` block before and after `COMMIT` or `ROLLBACK` and at each isolation level, as the same result or as the intended difference.** CTP starts each sql TC file with autocommit on, so without `autocommit off;` every statement commits at once and the TC never crosses a transaction boundary. A defect in what a snapshot sees, such as a statistic or a cached value that stays after a rollback, then goes unseen. Example: after `autocommit off;`, the TC deletes rows of `t`, runs `select count(*) from t;` in the same transaction, runs `rollback;`, and runs the count again.

**Leave out hints, parameters, data, and cases that neither the reproduction nor the check needs.** Each of them can change the plan or the output for a reason outside the issue, and the reader can no longer tell what the TC checks. The statements that restore what the TC changed are not extra, and the [writing rules](writing-rules.md#cleanup) keep them. Example: a TC that checks the rows of a `LEFT JOIN` sets no `print_index_detail=yes` and adds no `LIMIT 2` that the check does not use.

## Evidence in the answer file

**Choose data and queries that take the *bug path*, so that a build without the fix prints output that differs from the *answer file*.** A TC whose data never reaches the bug path passes on every build and misses the same defect when it comes back. How to run a TC on both builds and report it is in [Before the PR](../AGENTS.md#before-the-pr). Example: a TC for `ORDER SIBLINGS BY` gives some parents two or more children, and data that checks a sort or a rank has at least two distinct keys and one key that repeats.

**Print output that changes when a regression comes in: columns that tell the rows apart and values that differ between rows, not only a constant, all `NULL`, no rows, or a count.** A wrong value, or a row that takes the place of another, leaves a count and a constant column the same, so the answer file still matches. Example: `select id, v from t where a > 10 order by id;`, with a different `v` in each row, rather than `select count(*) from t where a > 10;` alone.

**When the TC checks an optimization or a new execution path, follow each query with a twin that skips only that path, so that the two results must match row by row.** A wrong result that the writer missed when making the answer file then shows as a difference between the two. The twin changes one factor, such as a `no_parallel_scan` hint, a copy of the table without partitions, or another join method. When a group of queries runs once under each of two settings, keep the statements of the two groups the same character for character, and write in the PR how many blocks of the two groups match; a change to one group alone breaks the comparison, and the answer file does not show it. When the two differ because of a defect that the TC does not check, the [writing rules](writing-rules.md#answer-files) say when the answer file may keep it as a *known wrong result*. Example: `select /*+ parallel(4) */ count(*), sum(a) from t where a >= 0 using index i_a;` followed by `select /*+ no_parallel_scan */ count(*), sum(a) from t where a >= 0 using index i_a;`.

**After you set a parameter or add a hint, check in the plan, the trace, or the result that it took effect and that the output shows the difference it makes.** The engine ignores a misspelled hint or a hint that names an index ambiguously, and a TC that passes when the value is ignored misses the regression. When a parameter or a hint was renamed, also check that the old name no longer has an effect. When the TC checks that two settings give the same result, add one query whose result differs between the two settings: without it, a setting that did not take effect makes every pair match, and the TC passes. Example: a query with `no_parallel_scan` shows no parallel workers line in its trace, and the same query without the hint right after it shows that line and returns the same result.

**Check that a statement that must be refused prints the error code of that refusal, not another error.** A statement that fails for another reason, such as a syntax error, also prints an `Error:` line, and the answer file then keeps the wrong refusal. Example: the answer file of an `ALTER TABLE … RENAME` that must be refused shows the code of that refusal, not the `Error:-493` that a typo in the statement prints.

**After a DDL, DML, or privilege change succeeds, check its effect with a SELECT, and after a refused statement, check that the catalog and the data did not change.** An error code or a success message alone misses a defect that reports one thing and does another, such as a refused statement that still changed part of the catalog. Example: after `grant select on t to u1;`, the TC selects the rows of `db_auth` for `u1`, and after a refused `alter table t rename to t_new;`, it selects from `db_class` that `t` still exists and `t_new` does not.

## Plans, hints, and data size

**For an optimizer or executor issue, put the plan or the trace into the answer file with `--@queryplan` or with `set trace on;` and `show trace;`, so that it shows the join method, the chosen index, and the parallel lines.** A query can keep its correct result and still turn slow, such as by a switch to a full scan or a parallel scan that no longer runs, and only the plan or the trace shows that. How to write the directive line is in the [writing rules](writing-rules.md#plans-and-traces), and which numbers CTP hides is under [What sql TCs cannot check](#what-sql-tcs-cannot-check). Example: `set trace on;`, then `select /*+ parallel(4) */ count(*) from t where a >= 0 using index i_a;` and `show trace;`, so that the answer file holds the parallel workers line under the `SCAN` line.

**Put `/*+ recompile */` only on a query that needs a stable plan, and write in the TC PR why it needs one.** A query that always gets a new plan never runs the path that reuses a cached plan, so when that path is part of what the TC checks, run the same query once more without the hint. What else the PR body holds is in [The PR](../AGENTS.md#the-pr). Example: a TC whose answer file holds the trace of `select /*+ recompile */ count(*) from t where a > 0;` says in the PR why that query needs a stable plan, and when the TC also checks the cached plan, it runs `select count(*) from t where a > 0;` once more without the hint.

**Fix the plan with a join hint when the join method or the plan is what the TC checks, and use no join hint when the TC checks only the result.** A join hint ties a result-only TC to one plan, and the check does not need it. Add the same query without the hint only when the plan that the optimizer picks on its own is also what the TC checks. Example: `/*+ use_hash */` in a case that checks a hash join in a subquery, and the plain query in a case that checks only the rows of that subquery.

**When a scenario must cross a *threshold*, build data that crosses it with a margin, and avoid large data.** Data just past the threshold falls back under it with a small change of row size or statistics, and a large table makes the run long. Write down the rows, the pages, the threshold, and the reason, in the place that the [writing rules](writing-rules.md#statements-and-comments) give. Example: `sql/_13_issues/_26_2h/cases/cbrd_27598.sql` builds its table `t_big` with 100000 rows in about 220 heap pages for the parallel heap scan threshold of 32 pages, and writes the rows, the pages, and the threshold in a `--` line above its `create table`.

## What sql TCs cannot check

CTP runs the TC files of a run one after another on one database ([Before the PR](../AGENTS.md#before-the-pr)), in one environment that `sql.conf` fixes. It compares the output of each file with its answer file as one string, after it removes only CR and LF and replaces the numbers of plans and traces with `?`. The checks below give results that change from run to run or that this comparison cannot see, and each rule says what to do instead.

**Give each SELECT that can return more than one row an `ORDER BY` on the whole select list or on a unique key, so that the rows come in one fixed order.** Without it, the scan or the degree of parallelism changes the order on the same engine, and the answer file fails without a regression. When `DISTINCT` or `GROUP BY` keeps one of several rows that tie, fix which one, such as with `MIN(id)`. When the collation of the grouped column treats different characters as equal, `MIN()` on that column can return either of them, so cast it to a binary collation, such as `min(cast(c as char(1000) collate utf8_bin))`. Example: `select grantor_name, object_name, auth_type from db_auth order by grantor_name, object_name, auth_type;`, not `… order by grantor_name;` alone.

**Keep values that change from run to run out of the answer file: the current date, time, and year, `RAND()`, OIDs, page and volume IDs, server log paths, and the whole content of a system catalog.** They differ on each run or machine, and a catalog also holds the objects and statistics that other TCs left. Print a value derived from them that stays the same instead. A time zone value assumes the `TZ='Asia/Seoul'` of the machines that run the TCs. Example: `select length(to_char(sys_datetime, 'YYYY-MM-DD'));` prints 10 on every run, and `select sys_datetime;` prints a new value each time.

**Write queries whose result does not depend on the machine, the physical order of rows, or timing.** The row count of a catalog or a system class depends on what other TCs left, a result that follows the physical order of rows or a hash layout changes with the storage, and `sleep()` does not order statements. A non-aggregated column outside `GROUP BY` can come from any row of its group, and one value can print in more than one form. Example: `select a, min(b) from t group by a order by a;`, not `select a, b from t group by a;`, and `select count(*) from db_class where class_name = 't';`, not `select count(*) from db_class;`.

**Print the number of rows with `count(*)` when it matters, because CTP removes CR and LF before it compares output.** Outputs that differ only in blank lines then compare equal. Example: `select count(*) from t where a > 0;` next to `select a from t where a > 0 order by a;`.

**Check a plan or a trace by its lines and their shape, not by a number in it.** CTP replaces every number in the plan of `--@queryplan` or a `.queryPlan` file and in the output of `show trace` with `?`, so cost, cardinality, rows, fetches, time, and the number of parallel workers all print as `?`. For the same reason, names that differ only in digits look the same in a plan, as the [writing rules](writing-rules.md#plans-and-traces) say. Example: the TC checks that the trace has a parallel workers line under the `SCAN` line, not that it shows 4 workers.

**Tell failed statements apart by their error codes, not by their messages.** With the default CTP setting, a failed statement prints one line, `Error:-<code>`, so two messages with one code look the same. `--+ server-message on` adds the message, unmasked up to `[CAS INFO`, so its text can change with the version or the environment. Example: two refused `ALTER` statements that name different columns print the same `Error:-<code>` line, and a SELECT on the catalog after each one shows which column it left unchanged.

**Judge a sql TC by its output, not by how long its queries run.** CTP does not compare time, and the load of the machine changes the time from run to run. A query that turns slow shows in its plan or its trace, as [Plans, hints, and data size](#plans-hints-and-data-size) says. Example: the TC checks that the trace shows an index scan, not that the query returns within 1 second.

**Put a check that sql cannot run into a category that can: concurrency into isolation, and a restart, a crash, or a setting read only at server start into shell.** CTP runs the statements of a sql TC one after another in one thread, even when the `@<connId>:` prefix splits them over connections, and `lock_timeout` is 10 seconds, so lock waits, deadlocks, and concurrent visibility belong to isolation TCs. sql TCs run in one environment that `sql.conf` fixes, so server restarts, crash recovery, running out of memory, `cubrid.conf` parameters that take effect only at server start, broker settings, and the database charset belong to shell TCs, and HA synchronization belongs to ha_shell TCs. Example: a check that a second transaction waits for a lock that the first holds is an isolation TC, and a check of a parameter that the server reads only at start is a shell TC.

## Model TCs

**Copy what a model TC does well, and write each point listed under "Differs" the way the [writing rules](writing-rules.md#new-tc) say.** The listed points break a writing rule, and a copy would carry the break into a new TC. Example: copy the `no_parallel_scan` twins of `cbrd_26722_index_overflow.sql`, and write its *header block* without the `'` of `key's` on line 5.

- `sql/_36_guava/cbrd_26722/cases/cbrd_26722_index_overflow.sql`: each query is followed by its `no_parallel_scan` twin, which puts a control into the answer file, and the header block says that CTP masks the digits of a trace, so the TC checks only the tokens of the trace.
  Differs: line 5 puts a `'` (`key's`) inside the header block.
- `sql/_13_issues/_26_2h/cases/cbrd_27598.sql`: in a few lines its header block states the cause of the crash, the fix, and the six cases, and each query is compared with its serial twin.
- `sql/_36_guava/cbrd_27100/cases/cbrd_27100.sql`: its header block states what the engine did before the fix (a default selectivity of 0.1), and each query is compared with its `parallel(0)` twin.
